BUILD THE DCS PROJECT DASHBOARD BUILDER

GOAL
Replace the "Build dashboard" placeholder tab (currently "under development") at
/dcs-system/project/:project_id/dashboard with a full dashboard builder where a user
composes charts from the project's collected form data, saves the dashboard on the
project, and views it live. Backend: dc_backend (Express 5 + native MongoDB driver,
no Mongoose). Frontend: frontend/src/systems/dcs (React + Tailwind, Recharts is
already installed).

CONTEXT (existing conventions that MUST be followed)
- Forms are versioned (dcs_forms: form_group_id + version, one is_active), submissions
  live in dcs_submissions with {form_group_id, version, data, submitted_at}. Records
  flagged is_test_data_generated_sss_ddd must NEVER be counted or sent to the frontend
  dashboards.
- Access control: use utilities/project_access.js. Only users whose resolved access
  allows a form may see charts built on it; the dashboard save/edit requires
  resolve_form_management(user, project).edit_project or the project owner.
- All aggregation must be done with native MongoDB queries ($match, $group, $facet,
  $bucket, $unionWith etc.) - no manual counting or slicing in JS.
- i18n: every new message key must be added to backend i18n (en/fr/kn) and frontend
  DCS i18n (en/fr/kn) with {{var}} interpolation where needed.
- Frontend design: reuse globals.css classes and Dcs* components (DcsButtonPrimary,
  DcsButtonOutline, DcsSearchableSelect, DcsConfirmDialog, custom SVG-designed
  dropdowns with animations - never native selects). System header bg #056daa on
  section headers, Montserrat titles, bordered white cards (#E0E0E0), reduced white
  glare (rgba(255,255,255,0.85) on blue banners). Fully responsive; below 760px
  panels go edge-to-edge.

FEATURE REQUIREMENTS

1. Dashboard model
   - New collection dcs_dashboards: one document per project
     {project_id, widgets: [...], layout, updated_at, created_at}.
   - Each widget: {id, title, form_group_id, chart_type, field_id(s), aggregation
     (count | sum | avg | min | max of a numeric field), group_by (a field, or
     submitted_at bucketed by hour/day/week/month), split_by (optional second
     categorical field for grouped/stacked series), filters (field/operator/value
     list), period (preset or custom from/to), sort, limit ("top N + rest"), size
     (w x h grid units), position.

2. Chart catalog (pick chart automatically-sensible, guided by data shape)
   Support these chart types, each with a short "when to use" hint shown in the
   picker, following the reference notes below:
   - Comparison: bar chart (default first choice; categories, same order of
     magnitude, axis starts at zero, warn above ~30 bars), column chart (short
     labels / few timestamps), grouped bar/column (two categorical variables, warn
     when too many groups), lollipop (many categories, space-saving), dot plot
     (multiple values per category, axis need not start at zero).
   - Time: line chart for many timestamps (reuse the existing "Submissions over
     time" bucketing: hour/day/week/month/year, week buckets anchored on the
     range's own start date), area chart, column chart only when few timestamps.
   - Correlation: scatter plot (two numeric fields), bubble chart (third numeric
     as size); heatmap matrix for two categorical fields (color = count).
   - Part-to-whole: stacked bar/column and 100% stacked, pie chart (only allowed
     up to 6 slices - auto-fold the remainder into "Other"), donut chart (same
     rule, center shows the total), waffle chart (percentages rounded to whole
     cells), treemap (hierarchical/cascading fields, e.g. Province > District).
   - KPI card: a single aggregated number with label (count/sum/avg) plus optional
     comparison vs previous period.
   The builder must VALIDATE chart-vs-data fit and refuse bad picks with a clear
   message (e.g. pie with 40 categories -> suggest bar; long labels on column ->
   suggest bar; two numeric fields -> suggest scatter).

3. Builder UX (edit mode)
   - "Add widget" wizard, step by step like the approval wizard: pick form ->
     pick chart type (cards with tiny SVG previews + when-to-use hint) -> pick
     fields/aggregation/group-by (only fields whose type fits the chart are
     offered: categorical = select/select_group/cascading, numeric = number,
     date = date/submitted_at) -> filters & period -> title & size -> live
     preview before adding.
   - Drag-free layout: widgets placed in a responsive grid; move up/down and
     resize via buttons (no drag library). Edit and remove on every widget with
     confirm dialog on remove.
   - Save button persists the whole dashboard (PUT, one document). Unsaved-changes
     indicator. Empty dashboard state with a friendly illustration + "Add widget".

4. View mode
   - Default tab view renders saved widgets with data fetched from one endpoint:
     GET /dcs/api/projects/:project_id/dashboard (config) and
     POST /dcs/api/projects/:project_id/dashboard/data with the widget list ->
     returns each widget's aggregated series in one response; aggregation runs
     per widget with native pipelines against the ACTIVE form version, excluding
     test data, respecting the viewer's per-form access (a widget on a form the
     viewer cannot see renders as a locked card, never leaking data).
   - Auto-refresh silently every 30s (reuse useSilentPolling). Loading skeletons,
     per-widget error state with retry.
   - Period filter in the dashboard header (reuse DcsPeriodFilter incl. custom
     range) that overrides widget periods; re-applies on every option click.

5. Cascading/location fields
   - For cascading and API-location fields, group-by must offer the LEVEL (e.g.
     group by District within Province X): implement with the same parent-trail
     logic used by test approvals (full ancestor trail conditions), aggregated in
     Mongo. Treemap uses the whole cascade as its hierarchy.

6. Endpoints (all authenticated, all access-checked, swagger-documented)
   - GET    /projects/:project_id/dashboard          -> config (or empty default)
   - PUT    /projects/:project_id/dashboard          -> save config (validated:
            widget shape, chart/field-type fit, limits; max 30 widgets)
   - POST   /projects/:project_id/dashboard/data     -> aggregated data for the
            requested widgets + period override
   - Never expose creator fields; strip internal flags from every response.

7. Quality bar
   - Backend: validate every input, warning_response/success_response/
     error_response pattern, new i18n keys in en/fr/kn.
   - Frontend: trilingual keys, no native selects, smooth expand/collapse
     animations, empty/loading/error states everywhere, works below 760px.
   - Prove it end-to-end with a mongodb-memory-server script (launchTimeout
     120000) that seeds a form + submissions (plus flagged test data that must be
     excluded), saves a dashboard with each chart family, fetches /dashboard/data
     and asserts the aggregated series (counts, sums, time buckets anchored to
     range start, pie "Other" folding, access-denied widget lock), then prints
     ALL DASHBOARD TESTS PASSED.
